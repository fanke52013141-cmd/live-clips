## 2. 发现的问题与修复

### 2.1 🔴 已修复：流复制路径容器时长错位（真机测试发现）

| | 内容 |
|---|---|
| **现象** | 草稿切片请求 2s→6s（4 秒），实际产出 **6.014s**——时长整整多了 seek 的偏移量 |
| **元凶** | `-avoid_negative_ts make_zero` 在 **`-c copy` + 输入端 `-ss` seek** 场景下，与 mp4 容器时间戳语义冲突：编码日志显示只处理了 4.1s（frame=180, time=4.10），但 mvhd 容器时长被错标为 6.014s。播放器会黑屏/进度条错位 |
| **定位过程** | 参数矩阵实验（5 组对照）：去掉 `negative_cts_offsets` 无效；**去掉 `avoid_negative_ts make_zero` 立即恢复 4.014s**；`-t` 移到 `-i` 前无效 |
| **影响范围** | ① `video_processor.build_draft_extract_command` copy 分支（OP-3.1 新增）② `create_collection` copy 分支（OP-3.5 新增）③ **上游遗留** `video_editor._extract_single_segment`（一直存在，此前无真机时长断言所以未暴露） |
| **修复** | 所有 `-c copy` 路径统一移除 `-avoid_negative_ts make_zero`；首帧黑帧防护由 `+negative_cts_offsets` 承担（两者语义冲突：make_zero 强制归零首帧时间戳，negative_cts_offsets 设计上允许负 CTS 偏移）。重编码路径保留 `avoid_negative_ts`（帧从 0 开始，无副作用，实测正确） |
| **验证** | 修复后草稿时长 4.014s ✓；合集 6.046s ✓；重编码切片 3.023s ✓ |
| **教训** | **任何涉及 ffmpeg 时长/时间戳的改动，必须用真实二进制跑时长断言**——mock 单元测试对此类问题零覆盖。已沉淀为可重复运行的 `scripts/verify_optimizations_integration.py` |
