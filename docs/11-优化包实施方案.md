## 1. 方案总则

### 1.1 "最大效益"的定义与排序逻辑

效益 = 四个可量化维度的改善，权重从高到低：

| 维度 | 为什么排这里 | 度量来源 |
|---|---|---|
| ① 成片可用率 | 黑帧/音画漂移/豆腐块是"一票否决"型缺陷——出 10 条废 3 条，用户感知是"不能用" | 基准人工抽检 |
| ② 端到端耗时 | 用户等待体验的核心；项目 README 已用耗时作为卖点 | `metadata/llm_usage.jsonl` timing |
| ③ 单条 LLM 成本 | 直接影响商业化毛利（ROADMAP credits 模式） | 同上 tokens/费用字段 |
| ④ 人工采纳率 | 选段质量的最终裁判 | Studio 状态 + 抽检 |

**排序原则（不是按收益大小，而是按 ROI 与风险）**：
1. **先修"确定性缺陷"**（参数级修正，零架构改动，收益立竿见影）；
2. **再做"稳定性"**（失败率下降 = 所有后续优化的地基）；
3. **然后"提速"**（感知最强）与"成本"（漏斗架构，改动稍大）；
4. **最后"质量升级"**（需要 A/B 验证，收益依赖前两步的数据）。

### 1.2 方法论（沿用项目既有惯例，不新造流程）

- **基线先行**：每个包动代码前，用 `scripts/fast_output_benchmark.py --baseline` 跑一次对照（项目已有完整基准设施，见 `docs/FAST_OUTPUT_BENCHMARK.md` 与 `benchmarks/fast_output/cases.json`）。
- **每包全量测试绿再进下一包**；每包一个 feature flag（settings），可独立开关与回滚。
- **新能力尽量落新文件**（`recall.py`、`llm_json.py`、draft 渲染路径），少改核心文件——降低与上游合并的冲突面（02 文档的 fork 漂移对策）。
- **许可红线**：auto-slice-video（MIT）可直接移植代码；clips-studio（AGPL）只重实现不抄写。

### 1.3 现状核对结论（避免重复造轮子）

实地核对发现以下机制**项目已具备**，不再列入优化包：

| 机制 | 现状证据 |
|---|---|
| 一次性选片（全量字幕单次调用）+ 长视频 60 分钟窗口**带重叠** + 跨窗去重 | `pipeline/clip_finder.py` 模块 docstring |
| 切点边界吸附（refine_timeline）与 select_clips 质量选择 | `pipeline/quality.py`，clip_finder 调用 |
| Whisper/SenseVoice 子进程隔离（独立 worker） | `utils/whisper_runtime.py`（"Standalone worker: launched with -S"）、`services/sensevoice_worker.py` |
| LLM 输出基础容错（code fence 剥离 + 正则修复 + 结构校验 + 重试 3 次） | `utils/llm_client.py` L64-193 |
| MP4 `+faststart`、`-avoid_negative_ts make_zero` | `utils/video_processor.py` L156-157/271、`video_editor.py` L180 |
| 阶段断点恢复（resume_from_step） | `services/processing_orchestrator.py` L727 |
| 提示词外置（PROMPT_FILES 机制） | `core/shared_config.py` |
| 基准测试集与对比报告 | `benchmarks/fast_output/` + `scripts/fast_output_benchmark.py --baseline` |

以下为**真实缺口**，构成优化包主体：编码器硬编码 libx264 无探针（`video_processor.py` L150/266）、无 `-vsync cfr`/`negative_cts_offsets`、无草稿档渲染、下载为整段单线程（`bilibili_downloader._download_sync`）、无信号召回层、无预算护栏、解析器缺逐条跳过与输出守卫。

### OP-0 · 基线校准包（0.5 天）

**目标**：让后续每一包都有"改造前 vs 改造后"的硬数字。

| # | 动作 | 说明 |
|---|---|---|
| 0.1 | 跑一次全量基准 | `python scripts/fast_output_benchmark.py --data-dir <测试目录>`，报告存 `benchmarks/fast_output/reports/`，作为**总基线** |
| 0.2 | 人工抽检清单补 2 项 | 在 FAST_OUTPUT 人工清单基础上增加：①首帧黑帧抽检（前 3 帧）；②音画同步抽检（拖动 3 个位置）——对应 OP-1 的验收 |

| 0.4 | token 成本基线 | 从 `metadata/llm_usage.jsonl` 汇总"每条成片平均费用"——对应 OP-4 的验收 |

**验收**：基线报告 + 两项新抽检项跑通；产出《优化前基线》小节追加到基准报告。

### OP-2 · LLM 稳定性包（2 天）—— 失败率下降的地基

**现状**：`llm_client.py` 已有 code fence 剥离、正则修复、结构校验、重试 3 次；**缺** json_repair 兜底、**逐条字段校验跳过**、输出形态守卫、计费错误不重试语义。

| # | 改动 | 文件 | 来源依据 |
|---|---|---|---|
| 2.1 | 解析器升级为四层防线：现有正则修复 → 新增 `json_repair` 库兜底 → 逐条 clip 字段校验（start/end/title 缺一丢弃该条并记日志，**其余照常出片**） | 新建 `utils/llm_json.py`，`llm_client.py` 与 `clip_finder.py` 行解析处接入 | auto-slicing 双防线 + Clips Kitty 分层 |
| 2.2 | 输出形态守卫：校验输出确为片段列表而非散文/解释文字，不合格直接报错进入重试 | `utils/llm_json.py` | AIMedia 输出守卫 |

### OP-3 · 渲染提速包（3-5 天）—— 感知耗时最大杠杆

**现状**：下载整段单线程（`_download_sync`）；渲染直接重编码；编码器硬编码 libx264（`video_processor.py` L150）；无草稿档。

| # | 改动 | 文件 | 效益 | 来源依据 |
|---|---|---|---|---|
| 3.1 | **草稿档渲染**：新增 `draft` 输出档——输入端 seek（`-ss` 在 `-i` 前）+ `-c copy` + `-map_metadata -1`；前端预览确认后才走精渲染 | `utils/video_editor.py` 新增 draft 路径 + API 加 `quality=draft` 参数 | 预览秒级出片，用户等待感知大降 | auto-slice-video/VideoCuter/irenmu 三方一致 |
| 3.2 | **下载分段 + 转写并行**：长视频下载按段落盘（yt-dlp 分段或 hls 分段下载），每段完成即提交转写任务——总耗时 ≈ max(下载, 转写) 而非两者之和 | `utils/bilibili_downloader.py` + `services/processing_orchestrator.py`（流式阶段） | **全方案最大单项耗时杠杆**（4h 素材可省 30-60 分钟） | StreamCap 分段录制 |
| 3.3 | **编码器探针 + 逐条回退**：启动时用最终渲染实际参数试编小黑帧，候选 NVENC→QSV→AMF→VideoToolbox→libx264；真实素材失败时原位替换编码器参数块回退 CPU | `utils/video_encoder.py` | GPU 机器渲染提速数倍；探针误判不再"整批 0 产出" | Clips Kitty 实测教训 |
| 3.4 | **慢源前置归一**：yt-dlp format 显式选 `vcodec^=avc1`（回退档排除 av01）；AV1/VP9 源入库前置转 H.264 | `utils/bilibili_downloader.py` ydl_opts | 避免 AV1 源把全链路拖慢 | Clips Kitty 实测教训 |
| 3.5 | **concat 快拼路径**：同参数片段合并走 `-f concat -safe 0 -c copy`（片尾拼接、多段合并） | 渲染包装链 | 拼接秒级 | auto-slicing |

**验收**：基准对比——端到端耗时差值表；草稿档单条 <10s（1080p 60s 片段）；全量测试绿；3.2 单独灰度（flag 控制）观察任务稳定性 3 天后再放开。
**风险提示**：3.1 的 copy 档切点吸附关键帧有秒级漂移——**只用于预览**，成片始终走精渲染（标注在 API 文档与前端 UI 上）。

| 6.3 | **通知防抖**：任务完成/失败通知模板变量统一、同事件防重、失败后延迟确认 | `tasks/notification.py`、`services/websocket_notification_service.py` | 通知不轰炸 | irenmu |
