## 1. 摘要（TL;DR）

1. **8 个项目按价值分三档**：
   - **A 档·直接可抄工程**：StreamCap（录制/下载/FFmpeg 工程参数）、auto-slice-video（弹幕密度粗筛算法，MIT）、VideoCuter（缓存协议/子进程隔离等实战规避）、auto-slicing（Agent 编排与提示词工程）——机制具体、成本低、收益明确。
   - **B 档·质量方法论**：Clips Kitty（clips-studio）——与 AutoClip 场景最接近的对标，每个痛点都有实测数字支撑（20 倍解码差距、985/1064 黑帧率、8/11 句中切点修复），是选段质量与渲染可靠性的最佳参考；**AGPL-3.0，只吸收思路不抄代码**。
   - **C 档·产品/架构设计**：bili-shadowreplay（影子回放原理，直播能力的蓝图）、irenmu/biliLive-tools（产品化设计：高能进度条、断播续传、webhook 枢纽、风控参数化）、AIMedia（LLM 成本治理与发布登录适配）。
2. **最有价值的组合拳是"三层漏斗"**（auto-slice-video + auto-slicing + Clips Kitty 三方共同印证）：**信号粗筛（弹幕密度/VAD/信号峰值，零 LLM 成本）→ LLM 语义精选（分批 + 防幻觉提示词）→ 双档渲染（流复制草稿秒出 / 重编码成片）**——同时命中 AutoClip"长视频耗时、LLM 上下文限制、选段成本、渲染速度"四大痛点。
3. **直播能力扩展的最短路线**（irenmu + bili-shadowreplay 结论）：第一阶段不做录制器，做 **webhook 处理枢纽**（消费录播姬/blrec 的文件事件 + 断播续传合并），把现有剪辑管线变成直播素材工厂；第二阶段再按 **HLS EVENT 归档**方案实现影子回放，实现"直播中划区间出片"。
4. **合规红线**：clips-studio 是 AGPL-3.0、irenmu 是 GPLv3，均**只吸收思路/产品设计，不复制代码**（与 02 文档对 hotclip 的处理一致）；AIMedia/StreamCap/VideoCuter/auto-slicing/bili-shadowreplay 许可证未逐一核实，**集成前必查**；auto-slice-video 已核实 MIT。

## 3. 逐项目分析与吸收清单

### 3.1 StreamCap —— 录制/下载/FFmpeg 工程参数库（A 档）

**定位**：FFmpeg + StreamGet 的多平台直播录制客户端，覆盖 40+ 国内外平台，桌面/Web/Docker 三形态，工程质量高（有 CI、清晰分层）。

**关键机制**（源码均在 `app/core/` 下）：
- **FFmpeg 录制参数模板**（`media/ffmpeg_builders/base.py`）：国内/海外两档（`rw_timeout=15s`、大 `analyzeduration/probesize`）、`-fflags +discardcorrupt+igndts`、断流重连三件套 `-reconnect_streamed -reconnect_at_eof -reconnect_delay_max 60`、`-protocol_whitelist` 白名单、移动端 UA；默认 `-c:v copy`，仅用户设码率才转码。
- **分段录制**（`recording/stream_manager.py`）：`-f segment -segment_time 1800 -reset_timestamps 1` 产出 `name_%03d.ts`；MP4 分段加 `-movflags +frag_keyframe+empty_moov+delay_moov`（可中断的渐进式 MP4）；事后 `ffmpeg -c copy` 纯封装转 mp4，零转码。
- **进程优雅退出**：Windows 向 stdin 写 `q` / POSIX SIGINT → 等 5s → `wait_for(15)` 超时才 kill；返回码白名单 `{0, 255}`（255=信号中断正常）；stderr 只保留尾部 64KB。
- **重连防抖**：录制时长 >25s 才允许重连检测，不足判错误——防"秒断死循环"。
- **按平台信号量限并发**：`defaultdict(lambda: asyncio.Semaphore(3))`，防单平台请求过密触发风控。
- **双层节流**：全局 180s 周期检测 + 每任务 loop_time（默认 300s）。
- **双下载路径互备**：ffmpeg 主路径 + httpx 流式直连兜底（`media/direct_downloader.py`）；codec 感知源选择（FLV 遇 h265 回退 HLS）。
- **磁盘熔断**：低于 2GB 全局停录 + 通知；**BackgroundService 收尾队列**：应用退出中把转码任务转入独立线程跑完。
- **流式视频服务**（`api/video_stream_service.py`）：Range→206 分块响应 + ETag/304 + TTLCache——浏览器 `<video>` 拖动预览的完整实现。
- **状态机字段设计**：`stopping_in_progress`（防"停止请求与自然完成"竞态）、`cumulative_duration`、`notified_*` 防重；后端与 UI 用 `UIBridge` Protocol + WeakSet 多会话广播解耦。

**吸收清单**：

| # | 借鉴 | 融入环节 | 解决问题 |
|---|---|---|---|
| 1 | **分段落盘 + 分片完成即提交转写** | 下载环节（`utils/bilibili_downloader.py` / 任务编排） | **最大耗时杠杆**：下载与 Whisper/FunASR 并行，总耗时 ≈ max(下载, 转写) 而非两者之和 |
| 2 | FFmpeg 弱网参数模板（两档）+ reconnect 三件套 | 下载/未来录制环节 | 弱网更稳、自动重连、坏帧丢弃不中断 |
| 3 | 优雅退出协议 + 可中断 MP4 封装 | 渲染环节 + Celery worker 管理 | 取消任务不产损坏文件；worker 重启无僵尸 ffmpeg |
| 4 | 返回码白名单 + stderr 尾部捕获 | 渲染/下载失败判定 | 255 不误报失败；错误日志有据不膨胀 |
| 5 | 重连防抖（最小有效时长门槛） | 下载重试策略 | 防"秒断死循环"烧资源 |
| 6 | 按平台信号量限并发 | 下载环节 | 多任务并发不触平台风控 |
| 7 | `-c copy` 零转码封装 | 渲染快速路径 | 封装级转换秒级完成 |
| 8 | Range/ETag/304 流式视频服务 | 成片预览 | 浏览器直接拖动预览，不必下载 ZIP |

### 3.2 AIMedia —— LLM 流水线工程化与成本治理（C 档设计、部分 A 档机制）

**定位**：Electron 图文创作工具（选题→AI 写作→去 AI 味→排版→多平台发布/托管），与 AutoClip 产品形态同构，价值在"AI 加工链"而非音视频。

**关键机制**（源码均在 `electron/` 下）：
- **generateCall 任务封装**（`ipc.cjs` L378-396）：requestId + AbortController + 同 key 重复提交拒绝 + 窗口销毁自动取消 + 分阶段进度事件——一套完整的"生成任务生命周期"。
- **多阶段管线与质量护栏**（`pipeline.cjs`）："不可变事实清单"（人名/数字/时间要求逐字保留）→ 生成 → 事实校核；**逐句补丁修复 + 编辑距离 >12% 整体回退**——防 LLM 借修复之名重写全文；`protectTerms` 占位符保护专名数字。
- **JSON 容错解析**：去 code fence → JS 风格正则修复 → 二次 parse → 字段白名单过滤。
- **预算护栏**（`qiling-budget.cjs`）：单次 Token/费用上限 + **提交前费用预估校验**（超限直接拒绝"未提交生成"）；`retryable:false` 语义——**计费输出永不自动重试**。
- **分层成本策略**（`docs/PRD.md` 8.3 节）：模板渲染与 AI 生图分工、快/精修模型路由、批量候选一次成稿、缓存复用——实测压到原成本 15-30%。
- **声明式多平台登录**（`platformLogin.cjs`）：`WEB_LOGIN_CONFIG` 字典（url/successRe 正则/会话分区/cookie 字段），新增平台=加一段配置；`withSession` 串行化 + `assertAccount` 身份校验防错投账号。
- **桌面数据安全**（`app-data.cjs`）：safeStorage 加密 + `.tmp+rename` 原子写 + 损坏保留不覆盖。

**吸收清单**：

| # | 借鉴 | 融入环节 | 解决问题 |
|---|---|---|---|
| 1 | generateCall 任务封装（取消/去重/分阶段进度） | Celery 任务层 + 前端任务面板 | 长任务可随时取消不挂起；防重复提交 |
| 2 | JSON 容错解析（code fence/白名单） | LLM 选段输出解析（`utils/llm_client.py` / `pipeline/clip_finder.py`） | 一个尾逗号不再毁掉整单 |
| 3 | 不可变事实清单 + 补丁式修复 + 编辑距离回退 | 标题/简介/话题文案环节（`pipeline/step4_title.py`） | 文案不编造视频里没有的内容 |
| 4 | 确定性清洗规则表先于模型 | 转写后处理（`utils/text_processor.py`） | 大量清洗零 token 成本 |
| 5 | 预算护栏 + 费用预估前置 | LLM 分析/AI 封面提交前 | "一个 3 小时视频烧掉一天额度"可控可配 |
| 6 | retryable:false 计费错误语义 | Celery 重试策略 | 失败重试不烧钱 |
| 7 | 声明式登录配置 + 会话分区 + 串行队列 + 身份校验 | B站投稿环节（`services/bilibili_publisher.py`） | 并发投稿身份错乱/错投账号/csrf 失效 |
| 8 | 原子写 + 凭证加密 + 损坏不覆盖 | Tauri 桌面配置/Cookie 存储 | 掉电不损坏、凭证不落明文 |

### 3.3 irenmu / biliLive-tools —— 直播工具链的产品设计样本（C 档，产品设计为主）

**定位**：直播一站式处理（多平台录制/弹幕/压制/上传/同步），初衷解决"录播工具碎片化"。GPLv3——**只吸收产品设计，不碰代码**。

**产品能力要点**（docs.irenmu.com，抓取 8 个页面）：
- **高能进度条**：按弹幕密度画进度条，切片工作流 = "看热度曲线 → 跳转 → I/O 标记 → 批量导出"；弹幕关键词搜索（文档直接建议搜"卧槽""6666"定位名场面）。
- **断播续传**：同房间 + 上一文件结束后 N 分钟内（默认 10 分钟）再次出现文件 → 视为同一场直播，合并为同一稿件多分 P。
- **录制结束立即重试**：本场录制时长 ≥1 分钟即中断的，立即复查一次流状态——两项目（与 shadowreplay）共同验证的漏录对冲策略。
- **Webhook 三事件契约**：`FileOpening / FileClosed / FileError`（含 filePath/roomId/title/platform 等字段），既能消费录播姬/blrec/DDTV 的事件，也能自定义生产——**不自己录制也能获得直播素材入口**。
- **风控参数化**：检查间隔 60s（文档教育"过短会风控"）、投稿最短间隔、上传线路测速、必剪 API 备用通道、预上传 406 两阶段处置。
- **无损 vs 精确双模式导出**：copy 快但受关键帧对齐限制 / 重编码帧级精确可压弹幕——把 trade-off 明确摆给用户。
- **通知防抖**：录制开始≠直播开始（一场一次）；结束通知延迟 3 分钟确认；模板变量驼峰/下划线双写法。
- **lossless-cut 项目格式互通**（.llc）：零成本接入切片 man 生态。

**吸收清单**：直接对应"直播能力第一阶段"路线（见第 4.4 节）。

| # | 借鉴 | 融入环节 | 解决问题 |
|---|---|---|---|
| 1 | Webhook 枢纽（消费 FileClosed + 断播续传合并） | 新增"直播素材入口" | 不写录制器即可接入直播回放文件 |
| 2 | 弹幕密度高能进度条 + 关键词搜索 | 前端候选列表 + LLM 选段输入 | 人与 AI 共用同一信号源定位名场面 |
| 3 | 断播续传时间邻近合并 | 素材聚合 | 分段/短暂下播的碎片文件合成一场 |
| 4 | FileError 事件标注坏文件 | 任务编排 | 坏文件不阻塞流水线 |
| 5 | 无损/精确双模式导出 | 渲染环节两档 | 快速预览确认后再跑慢渲染 |
| 6 | 投稿最短间隔/线路选择/风控文档 | B站投稿（`bilibili_publisher.py`） | 对抗平台风控参数化 |
| 7 | 通知防抖 + 模板变量标准化 | 通知环节 | 不轰炸用户、文档心智统一 |
| 8 | ejs 文件名/标题模板 + 四字节字符兜底 | 输出组织 | Windows 路径不炸、批量可检索 |

### 3.4 bili-shadowreplay —— 影子回放原理（C 档原理蓝图）

**定位**：缓存直播流并实时编辑投稿——直播进行中即可回放任意历史时刻、划区间出片，"整个流程压缩到分钟级"。Tauri 2 + Rust，栈不匹配，**吸收原理不搬代码**。

**核心原理——本地 HLS EVENT 归档**（`src-tauri/crates/recorder/src/core/hls_recorder.rs`）：
- 录制即产出"只增不减的 m3u8（EVENT 型）+ 1 秒级分片"；**归档本身就是回放源**，没有"完整文件"中间态——切片直接消费已缓存分片（copy 优先），这就是"分钟级出片"的原因。
- **原子发布次序**（正确性关键，`recording-storage.md`）：先写分片字节 → 成功后才发布引用它的播放列表——回放端永远拿不到悬空引用。
- `.sequence` 文件持久化断点续录；坏分片（缺 SPS/PPS）字节级追加修复；Twitch 广告分片剔除（`#EXT-X-DATERANGE`）；分辨率/编码变化强制开新归档。
- **场次两级模型**：`platform_live_id`（B站用 live_start_time）→ 多个分段归档 → 回放按 parent_id 拼接——主播网络抖动不会被切成多个不相关项目。
- **回放服务**：`playlist.m3u8?start=&end=` 服务端按秒区间裁剪播放列表返回。
- **选区物化**（`recording_materialization.rs`）：切片前把选区覆盖分片+继承依赖拷到临时工作区（租约+drop 清理），归档可安全放 S3。
- 弹幕 JSONL 批量落盘（5s/64KiB）+ 预览旁路不被背压阻塞；AI Agent 提示词"**交叉验证字幕、弹幕密度和关键词；不要臆造时间点**"；MCP 工具 readonly/destructive 分级 + 执行边界二次校验 + **只存草稿不代发**。
- **AI 封面分工**：均匀抽帧（跳黑屏头）→ vision 模型只输出 {帧号, 样式, 位置} JSON（失败 JSON 修复重试 → 降级默认帧+warning）→ 前端 canvas 压字——**LLM 只做选择不做像素生成**。
- **Whisper 置信度重试**：低置信片段加大 beam 重试 + 200 字滚动上下文抑制幻觉 + 15 字/行。
- **投稿状态机**：draft→exporting→posting→posted/failed；**按时间轴 hash 缓存渲染结果，重试复用**。

**吸收清单**：见第 4.4 节直播路线第二阶段；此外 AI 封面分工、Whisper 置信度重试、MCP 安全分级、投稿渲染缓存四项在现有管线内即可用。

### 3.5 Clips Kitty（clips-studio）—— 最接近的对标，实测数字驱动的工程决策（B 档方法论；**AGPL-3.0 只吸收思路**）

**定位**：本地化 Opus Clip 替代品（Windows 桌面 + CLI/API/MCP），链路与 AutoClip 几乎完全重叠（贴链接→下载→转写→LLM 选段→竖版说话人跟踪→词级字幕→文案→Upload-Post 发布）。README 实测：单 PC 19m38s 出 38 条剪辑；2h 视频云端成本约 $0.11。

**最有价值的实测数字**（全部来自源码注释）：
- cv2.VideoCapture 读帧 vs FFmpeg `-hwaccel` + `select` 滤镜抽帧：10.16 CPU 秒 vs 0.94 CPU 秒——**20 倍差距**（`video/encoding.py` sampled_frames）。
- 首帧黑帧修复前：1064 条剪辑中 985 条 AAC priming 滞后 10.7-23.2ms（`encoding.py` concat 注释）。
- 说话人重检测 vs 复用跟踪框：+452% vs +15% 耗时（`video/asd.py`）。
- 句边界回退规则：11 个入选剪辑中 8 个原本会切在句中（`analysis/highlights.py`）。

**吸收清单**：

| # | 借鉴（思路） | 融入环节 | 解决问题 |
|---|---|---|---|
| 1 | `-vsync cfr` + `aresample=async=1` | 渲染命令构造（`utils/video_encoder.py`） | B站下载源 VFR 导致竖版跟踪音画漂移 |
| 2 | 终稿 movflags `+faststart+negative_cts_offsets` + concat 用 `-copyts` | 渲染输出/发布包封装 | 上传平台开头黑帧（实测 985/1064 中招） |
| 3 | GPU 编码器"真实参数探针 + 逐条 CPU 回退" | 编码选择 | 探针过了但真实素材被拒→整批 0 产出 |
| 4 | 帧读取走 FFmpeg 硬解管道（非 cv2） | 说话人跟踪/视觉信号取帧 | 20 倍 CPU 节省 |
| 5 | 慢编码源（AV1/VP9）前置转 H.264；yt-dlp 显式选 avc1 | 下载/入库 | 后续每阶段重复软解码 |
| 6 | 三级并发：转写期并行提信号、渲染期并行、队列预下载（join 带超时） | Celery 编排 | GPU 空转与串行等待 |
| 7 | **双候选池**：LLM 转写池（1200s 块 60s 重叠）+ 信号峰值池（视频内百分位 85、预算 max(12, 时长//300)、按峰值强度取） | 高光筛选（`pipeline/step3_scoring.py`） | 漏掉"说得平淡但现场爆炸"的时刻；长视频后段峰值无名额 |
| 8 | **信号时间线文本化**注入提示词：`[244s] AUDIO spike (99th pct, burst cluster)` | LLM 提示词构造 | 不识像素的 LLM 也能推理音视频语境 |
| 9 | **rerank 终选**：top-8 一次调用两两排序，结果只加不减（0-6 奖励） | 选段后处理 | 小模型绝对打分扎堆，相对排序更可靠 |
| 10 | **三闸门查重**：时间戳重叠>40% / 文本相似>70% / segment 复用>40%，**拒绝原因落库可审计** | 选段去重 | 多块分析重复选段；结果可解释可调参 |
| 11 | **句边界吸附**（8s 回看、2s 停顿断句、起点不越过被选中行、多语言句末符号） | 切点修正（`utils/word_timing.py`） | 实测 8/11 切点在句中→成片开头半句话 |
| 12 | score 提示词**防膨胀**（"多数应低于 50"）+ hook **防幻觉锚定**（必须引用实际说出的话） | 提示词模板 | 分数虚高失去区分度；标题幻觉翻车 |
| 13 | 提示词全部外置为可编辑文件 | 提示词管理 | 用户/运营免改代码调风格，便于 A/B |
| 14 | LLM 鲁棒性分层：容错提取→重试一次→跳过并记录（绝不崩整跑）；窗口打分每批 8 个按时间匹配 | LLM 调用封装 | 本地小模型结构化输出不可靠 |
| 15 | 三级预览：CSS/rAF 即时覆盖层 → 低清草稿渲染（draftStale 提示）→ Apply 终渲 | React 剪辑工作台 | 改样式秒看，重渲染只发生在确认前 |
| 16 | **非破坏 EditList 数据模型**（keep/mutes/volume/fades/speed/hook/music 全参数化 + clamp 校验 + remap 时间映射）+ **单次 filter_complex 应用**（loudnorm 先于 fade） | 渲染前编辑层 | 任何编辑可撤销可重渲；一次 FFmpeg 完成全部处理 |
| 17 | BGM `sidechaincompress` 人声闪避（threshold 0.02, ratio 12） | 音频处理 | BGM 压人声 |
| 18 | 词级 ASS 直接构建 + **单次编码同时裁剪与烧录** + **按语言换字体**（中文→Microsoft YaHei） | 字幕环节（`utils/subtitle_processor.py` / `services/output_captions.py`） | 中文烧录豆腐块永久烙进视频；省一次编码 |
| 19 | 说话人判定唯一权威=专用 ASD 模型，口部移动只作 tiebreak；换人"切镜"不"摇镜"；复用跟踪框+只对争议区间打分 | 竖版访谈式取景 | "跟随最大人脸"误跟旁观者；成本 +15% vs +452% |
| 20 | 阶段状态机：每阶段先提交 SQLite 再继续；**job 入队时快照配置，worker 深拷贝** | Celery/Redis 任务模型 | 崩溃从失败阶段恢复；中途改配置不致前后不一致 |
| 21 | 短任务插队 + 实测驱动的耗时预估（样本不足报 confident:false） | 队列/前端 | 重渲/翻译不被长任务压后；预估不胡编 |
| 22 | 可选子系统 `available()` 门控：权重缺失只是功能降级，不报废整单 | 各 AI 环节封装 | 用户环境千差万别 |
| 23 | 下载产物临时名 + 可读性验证才 rename + 按文件锁 | yt-dlp 下载/本地导入 | 半写文件被误认为成品 |
| 24 | "本地 API 即产品面"：REST + WebSocket 进度 + webhook + MCP 同一引擎 | CLI/MCP/Tauri 多端架构 | 桌面端只是 API 的一个窗口，第三方零改造接入 |

### 3.7 auto-slice-video（autosv）—— 弹幕密度"免费召回层"（A 档，MIT 可直接集成）

**定位**：PyPI 包（MIT），把 B站 ASS 弹幕文件当"热度信号源"，滑动窗口找弹幕最密集时段并流复制切片。无 AI、零 LLM 成本。

**关键机制**：
- 弹幕解析 30 行代码（`autosv.py: extract_timestamps()`）：逐行取 `Dialogue:` 时间列。
- 核心算法（`calculate/sliding_cpu.py: find_dense_periods_cpu()`）：每秒弹幕计数 → 滑窗密度 → 降序 → **重叠约束贪心**（与已选片段重叠 > max_overlap 丢弃——保证 top-N 不是同一波高能）。
- GPU 自动降级（`calculate/selection.py`）：`nvcc -V` 探测 → numba CUDA（3 万条弹幕 2s vs CPU 33s，16.5 倍，仅 55MB 显存）→ 失败静默回退 CPU。
- 快切（`slice/slice_video.py`）：`-ss` 输入端寻址 + `-c copy` + `-map_metadata -1`。
- 输出命名 `{起始秒}s_{原名}` 可溯源；CLI 与纯函数 API 同核双入口。

**吸收清单**：

| # | 借鉴 | 融入环节 | 解决问题 |
|---|---|---|---|
| 1 | **弹幕密度作为"免费高光先验"**：贴 B站链接时同步抓弹幕，滑窗密度出 top-K 候选区间，**只把候选区间的字幕交给 LLM 精选** | 高光筛选前置召回层（`pipeline/clip_finder.py` / `step3_scoring.py` 之前） | LLM 上下文限制 + 选段成本：4h 视频字幕几十万字，先粗筛到 10-20% 再精选，token 成本降一个数量级；弹幕=真实观众投票，质量反而提升 |
| 2 | 重叠约束贪心 | 多片段输出逻辑 | N 条高光互相重叠、内容同质化 |
| 3 | GPU 探测自动降级 | Celery worker 能力探测 | 桌面用户机器各异，有 N 卡自动加速，无卡不报错 |
| 4 | 输入端 seek + `-c copy` 两段式快切 | 渲染"速度档" | 草稿/预览秒出片 |
| 5 | MIT 许可 | —— | 可直接引入代码（唯一已核实可抄代码的仓库） |

**局限**：弹幕方案只适合弹幕密集内容（直播/热番）；访谈/知识类弹幕稀疏即失效——**必须做成可选召回通道而非唯一判定**。

## 4. 横向综合：四大主题

### 4.1 主题一：速度与成本 —— "三层漏斗"（最高优先级）

四个项目独立收敛到同一架构，可视为长视频自动切片在成本/质量/速度上的实用平衡点：

```
第 1 层 · 信号粗筛（零 LLM 成本，秒级）
  弹幕密度滑窗（auto-slice-video）＋ 信号峰值池（Clips Kitty：音量/运动/笑声，
  视频内百分位 85 阈值，预算 max(12, 时长//300)）
  → 输出 top-K 候选区间（约占原片 10-20%）
第 2 层 · LLM 语义精选（只看候选区间字幕）
  VAD 预切分（auto-slicing）＋ 分批带 overlap（批内 5000 字符预算）
  ＋ 防幻觉锚定（区间取自输入时间戳/hook 引用原话）
  ＋ rerank 相对排序（Clips Kitty：top-8 两两对照，只加不减）
  ＋ 三闸门查重 + 句边界吸附
第 3 层 · 双档渲染
  速度档：输入端 seek + -c copy 流复制（秒级草稿，irenmu/VideoCuter/auto-slice-video
  三方一致；代价=关键帧对齐漂移，仅供预览）
  精度档：现有渲染管线（-vsync cfr / faststart / 单次编码裁剪+字幕）
```

**对 AutoClip 的映射**：第 1 层插在 `pipeline/clip_finder.py` 之前作为召回层；第 2 层强化 `step1_outline/step2_timeline/step3_scoring` 的提示词与后处理；第 3 层在 `utils/video_editor.py` / `video_encoder.py` 增加"草稿档"，前端预览确认后才走精渲染。

### 4.2 主题二：选段质量 —— 多信号 + 相对排序 + 可审计

- **信号融合公式**（Clips Kitty）：`final = 0.30·text + 0.20·visual + 0.20·reaction + 0.20·audio + 0.10·engagement`，信号按视频内百分位秩归一（安静播客与尖叫直播都产生有意义的峰）；奖励类信号"只加不减"。
- **弹幕作为与转写同级的信号**（irenmu 高能进度条 + BSS Agent 提示词 + auto-slice-video 算法三方印证）：密度曲线/SC/礼物峰值注入 LLM 上下文，同时把"高能时刻列表"直接呈现给用户——人与 AI 共用同一信号源。
- **查重与边界**：三闸门查重（40%/70%/40%，拒绝原因落库可审计）+ 句边界吸附（8s 回看/2s 停顿断句/起点不越过被选中行）。
- **提示词工程汇总**（四项目可合并成一套模板规范）：垂类正/负例带原话句（VideoCuter）、防分数膨胀（Clips Kitty）、hook 防幻觉锚定（Clips Kitty）、标题 few-shot+人设注入（auto-slicing）、信号时间线文本化（Clips Kitty）、时间戳取自输入（auto-slicing）、提示词外置可编辑（Clips Kitty）。

### 4.3 主题三：可靠性工程 —— "防御性设计"清单

跨项目反复出现、值得一次性纳入工程规范的模式：
1. **任务生命周期**：requestId + 取消传播 + 分阶段进度 + 窗口销毁自动取消（AIMedia）+ 状态机字段（取消竞态/累计时长/防重，StreamCap）。
2. **进程治理**：ffmpeg 优雅退出协议（q/SIGINT→15s kill）+ 返回码白名单 {0,255} + stderr 尾部 64KB（StreamCap）；ASR 子进程隔离（VideoCuter）。
3. **缓存与恢复**：每阶段产物落盘、任务从任意阶段恢复（VideoCuter）；阶段先提交 SQLite 再继续（Clips Kitty）；投稿按时间轴 hash 缓存渲染结果（BSS）。
4. **数据安全**：临时名+可读性验证才 rename（Clips Kitty）；原子写+损坏不覆盖（AIMedia）。
5. **LLM 输出防线**：容错解析（三层）→ 重试一次 → 跳过并记录（绝不崩整跑）（Clips Kitty/VideoCuter/AIMedia 三方一致）；json_repair+字段校验（auto-slicing）；编辑距离回退（AIMedia）。
6. **成本防线**：预算护栏+费用预估前置（AIMedia）；retryable:false 计费错误不自动重试（AIMedia）；GPU 探测自动降级（auto-slice-video/VideoCuter/StreamCap）。
7. **降级不失败**：可选子系统 available() 门控，权重缺失只是功能退化（Clips Kitty）。
8. **MCP 安全**：相对路径沙箱（auto-slicing）+ readonly/destructive 分级 + 执行边界二次校验 + 只存草稿不代发（BSS）。

### 4.4 主题四：直播能力扩展路线（未来方向，两阶段）

**第一阶段（不写录制器）——"处理枢纽"模式（仿 irenmu）**：
1. 定义"录制文件就绪" webhook 契约（FileOpening/FileClosed/FileError），消费录播姬/blrec 等第三方工具的事件——**不自研录制协议逆向，快速获得直播素材入口**；
2. 断播续传时间邻近合并（≤10 分钟同场合并分 P）+ 场次模型（platform_live_id → 多段拼接）；
3. 弹幕文件（录播姬 .xml）接入密度信号 → 高能进度条 + LLM 选段特征；
4. 现有"转写→选段→渲染→发布"管线原样复用，新增 Celery chain："收到文件 → 自动转写 → 自动选段 → 候选列表通知用户"。

**第二阶段（自研录制）——"影子回放"模式（仿 BSS）**：
1. 本地 HLS EVENT 归档：1s 分片 + 只增不减 m3u8 + `.sequence` 断点 + **原子发布次序（先分片后列表，必须照抄）**；
2. 回放服务 `playlist.m3u8?start=&end=` 服务端区间裁剪；
3. 选段/渲染直接消费播放列表——复用现有"高光时间段 → 渲染"流程只需把时间段映射到分片，实现"直播中划区间出片"；
4. 开播检测参数照抄两家共识：轮询间隔最小 10-20s+抖动、失败保持旧状态、录制中断≥1 分钟立即重查、按平台信号量限并发。

**贯穿**：AI 封面采用 BSS"模型选帧 + 前端合成 + JSON 修复降级"分工（比文生图便宜稳定）；LiveEnd 触发"自动整场处理" Celery chain + webhook 对外通知。
